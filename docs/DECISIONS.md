## D39 — Bounded Arc indexing and read freshness (2026-09-09)

A read-only Arc observation found twenty blocks in ten seconds, while warm public RPC reads took approximately 180–223 ms. The previous one-block worker needed several serial calls per block and could fall behind indefinitely. An initial sixteen-block batch improved throughput, but live operation still accumulated a backlog. Profiling measured 248 SQL queries for sixteen blocks. The final worker uses up to sixty-four confirmed blocks, at most eight outstanding header reads, one bounded range log request and four activation getters. Validate each log against the linked headers and transaction identities, then freshly recheck the canonical tip. Event-containing blocks retain ordered atomic commits; consecutive authenticated empty blocks share an atomic commit with all headers, coverage rows and notifications retained. Existing rollback, resync, payload and retry bounds remain. A real isolated-schema 64-block window completed in 4.334 seconds using forty SQL queries; this finite measurement does not guarantee sustained provider capacity. [Focused indexer evidence](../apps/indexer/test/batch-throughput.md).

Exact head-minus-two freshness also rejected normal RPC/indexing delay on this subsecond chain. For Arc only, accept an indexed cursor two through eight blocks behind the observed head while retaining the ten-second database age bound. Share the policy across API, wire schemas and SDK. This is a bounded availability decision, not finality or permission to trade on stale state. Preserve canonical historical pins, complete coverage, pinned payload equality, minimum two confirmations, twenty-second quote expiry and fresh wallet transaction reviews. Non-Arc profiles retain exact head-minus-two behavior. Payment source cursors may advance monotonically around the same canonical pin; rewinds, conflicting hashes and unconfirmed final cursors remain failures. Actual live throughput and financial receipts must still be observed separately.

The user's browser blocked the otherwise working public Blockdaemon endpoint. Arc application reads and simulations now pass through a bounded, read-only Next route on the application's own origin. The route accepts only the runtime manifest's verified provider and deployed call targets; it cannot sign, broadcast, select arbitrary upstream URLs or apply state overrides. This refines D40's transport path without changing the authenticated deployment or its selected upstream. Wallet-owned requests/submission retain their provider and explicit user actions.
