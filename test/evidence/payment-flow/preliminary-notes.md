# Preliminary payment workflow checks

These observations precede the final checkpoint and do not replace it.

- The new SDK test initially failed to import the not-yet-implemented payment review module (expected red stage).
- The first implemented focused run passed 12/13 tests. Its failed assertion expected an allowance-change error when reusing an already-consumed review. The implementation correctly rejected reuse first; the test now also creates a separate unused review before changing the allowance. The next focused five-test run passed, followed by all eight payment-review tests.
- A first four-browser-test run passed while further source edits were still underway. It is not the frozen final source checkpoint.
- The expanded browser run passed 8/9. The reload case failed in its RPC fixture with `page.evaluate: Execution context was destroyed, most likely because of a navigation`. The fixture queried page session storage from a receipt request while navigation destroyed that page. The retained [context](preliminary-reload-context.md) and [screenshot](preliminary-reload.png) belong to that failed run.
- The fixture now records submitted transaction parameters through an explicit Playwright binding into the test runner. Receipt responses no longer depend on a navigable page execution context. Production receipt recovery code was not changed to address this test-harness failure.
- Two preliminary TypeScript issues were corrected: a widened review-stage literal in the new SDK object and nullable/optional fields in the browser wire fixture. No successful build is inferred from those failed checks.
- The [initial frozen checkpoint](initial-checkpoint/checkpoint.json) passed 100 SDK, 7 shared and 30 browser checks, production build and workspace types with 708 unchanged authored inputs. It precedes the two subsequent adversarial checks and is superseded by the final checkpoint.
- [Both adversarial checks failed before the fixes](edge-red.txt): switching A→B→A revived the earlier review, and a transaction response with the expected contents but a different own hash was accepted as confirmation. The exact [test](edge-red-test.ts), [controller](edge-red-usePayment.ts), [RPC port](edge-red-paymentPort.ts) and [receipt-state context](edge-red-receipt-context.md) are retained. Context changes now advance a permanent intent generation and discard unsigned reviews; receipt validation binds the queried/returned hash, transaction/receipt block and payer/target as well as calldata/value. Submitted hashes remain recoverable across a wallet change.
- Final staged-byte verification found one pre-existing `Liquidity.module.css` newline difference: the worktree had one CRLF while the cached Git blob had LF. Its contents were equal ignoring that carriage return. The unchanged tested worktree bytes were explicitly restaged under the repository's `-text` rule; no design or functional change was made. [Diagnostic](staging-diagnostics.json).
